## 2. Background context (everything you need from the v1 documentation)
All values in this chapter are historical v1 records. Use them to locate code, understand the feedback and write regression tests. Verify every path, command and number against the repository and a fresh capture before relying on it.

### 2.1 Project, requirement and scope
- Fightclub migrates client websites from Concrete CMS to Framer. Designers must rebuild each page with reusable native Framer components and styles that preserve source text, typography, colours and spacing. A screenshot or HTML embed is not an acceptable result.
- The pipeline captures a public page (screenshots, saved HTML, DOM, measured geometry, browser-computed styles), groups the data per section, and gives it to an AI agent that builds styles and components in Framer.
- Requirement US 5 (GitHub issue #20, “Capture step of migration pipeline”): As a designer, I want text, typography, colours, and spacing to be mapped to the correct components and reusable styles, so that less manual correction is needed. Issue acceptance criteria: a list of data types and why they are important; a working extraction script for those data types; a working script for CSS data. Open question in the issue: which data still needs to be digested.
- Out of scope: CMS migration, multiple pages, link destinations, functional forms, SEO, alt-text/accessibility migration, video/lightbox behaviour and interaction states (menus, accordions, tabs, carousel slides, sticky/scroll states). Data about these may be kept as reference only.

### 2.4 v1 capture data fields
structure.json per node: tag, domId (HTML id or empty), classes, selector (CSS path from html with :nth-of-type), parentId/order/children, box (document x/y/width/height incl. scroll, rounded to 0.01px), render (display, visibility, opacity, position), traits, generated node ID, text/images/alt/form-field details. File level: metadata (url, slug, viewport, state, roots), sectionShell (ancestors wrapping clips), warnings (e.g. section-unassigned, unsupported-boundary).
computed.json per node: line-height, letter-spacing, font weight/size/family, text-transform, border-radius, box-shadow, borders, opacity, gradients, padding, margin, gap, colours/backgrounds. Missing in v1 and needed in v2: type scale, colour roles (proposals only), font sources/availability/weights, spacing scale with occurrence counts. Design notes: the structure file is large because of measurements; elements.json is not needed to find a section.

### 2.6 Feedback to implement
From the evaluation, design review and the author's notes (traced to F01–F13 in chapter 4):
- Capture widths without developer confirmation; keep the step that discovers breakpoint widths. Output one breakpoint per run to make testing easier; each breakpoint gets its own digest. Reproduce breakpoints directly, never derive them from mobile.
- Capture every button and field as variants of itself.
- Question whether the coverage check matters and what can go wrong without it; remove it from the pipeline and test the script instead.
- Stop reading the same things twice (step 4 re-reads nodes to compute styles).
- Decide whether proposed cross-width matches should be removed (decision: removed).
- Document how nodes are simplified.
- The clip digest takes in too much; reduce data to what the rebuild needs and measure the effect.
- Instead of a data library plus a map the agent searches, produce one digest per component with everything the builder needs, so it never stops mid-task to look something up. First compose an inventory of the data needed per metric, then make the scripts extract exactly that, without junk.
- Agree a versioned digest contract with a worked example and generate digests by script; document node-ID lifetime.
- Dismiss the cookie banner before capture.
- Keep asset/media references and links with the section data; omitting images did not save time.
- Specify Framer tools, inputs, outputs and failure handling; provide setup instructions, tool versions, font/asset handling, error behaviour and a component inventory for handoff.
- Target: match or beat the baseline on M3–M13 and M18 at the evaluation width, keep M2/M14–M17, generation under 15 minutes.
- Documentation style: numbered sections, described tables, conclusions in question → evidence format.

## 6. Digest and extraction contract
Create docs/poc-v2/digest-contract.md, a machine-readable schema and one validated button example using real capture values. Adapt storage paths to repository conventions.
Each component digest must contain:
- schemaVersion, captureId, source URL/final URL, language, timestamp, viewport, state and capture configuration.
- Component ID/type, source root and node provenance; included node hierarchy/order and capture-local IDs. Document that IDs are not assumed stable across new captures.
- Exact visible text and styled runs; explicit label-node styles for buttons and fields.
- Resolved typography, spacing, colours/fills/borders, measured geometry, layout/position/stacking, media and relevant pseudo-elements. Store only applicable fields, but distinguish zero, empty, unsupported and missing.
- Resolved reusable style/token values beside their references. Token names/colour roles are proposals; measured values stay unchanged.
- Screenshot/crop references, original and usable asset paths/URLs, natural dimensions, font availability, warning/error records and unsupported static features.
Extract structure, styles and geometry from the same settled browser state. Avoid duplicate DOM traversals and unnecessary file reloads. Keep the full evidence outside normal builder context; the builder consumes a small digest with directly available assets, not a map requiring repeated searches.
Simplification rule: remove a wrapper only when it has no meaningful text/content, no paint/pseudo-element, no spacing/layout/transform/clipping/stacking effect, and its children retain equivalent order and geometry. Preserve a provenance mapping. Keep styled labels and visually significant ancestors. Test hidden nodes, display-contents wrappers, flex/grid wrappers, absolute children and negative margins.
Make extraction generic: Yellow Hive values belong in fixtures, not hard-coded production logic. Historical values such as Lexend/18px/700/21px and 2px borders are regression clues; remeasure the chosen Dutch source before treating them as current truth.

## 7. Fast component-first implementation loop
Implement selectors/filters for one component, one viewport, one state and cache frozen capture inputs. Discover and use existing tooling; add the smallest missing harness rather than replacing the repository stack.
- Establish baseline tests, then add a failing regression for the smallest known defect.
- Start with button extraction → digest → Framer style application → isolated preview → metric assertions.
- Cover each observed button variant and one visible field if present. A missing field on the source is explicitly not applicable, not fabricated.
- Fix only the failing stage. Rebuild only affected definitions and dependants. Reuse unchanged captures/assets.
- Once buttons pass, exercise a typography block, a card/media component and a complex two-column/stacking section. Then process all sections found in the frozen one-width inventory.
- After each fix, run the targeted tests and relevant regressions. Keep a machine-readable criterion ledger with pass/fail/blocked/not-applicable, expected/actual values and evidence paths.
- Run the complete local suite at milestones and before delivery. Run one final one-width component batch smoke test; do not repeat a whole-page build after every small change.
Do not loosen thresholds, delete failing tests, reduce the component inventory or mark unavailable measurements passed. Fix the generic extractor/digest/builder cause instead of patching each output manually. If three attempts produce no progress on the same failure, investigate the root cause or alternate supported component-level approach. Stop only that blocked line when external access, fonts/licensing or unsupported APIs require user intervention; finish independent work.

### 7.1 Subagents when the task becomes too big
You may start subagents (Cursor background agents or parallel agents) when you judge that the work no longer fits comfortably in one context, or when independent work can run in parallel. Typical triggers: your context is filling with capture data, a single failure investigation is crowding out the main loop, or several components/fixtures can be built independently.
Good units to delegate: the node-data-to-metrics research document; the digest schema and validator; consent/settling fixtures; unit tests for one metric group; extraction for one component type; a root-cause investigation of one failing criterion.
Rules:
- You remain the orchestrator and owner of the feature branch. You decide acceptance; subagents report evidence, they do not mark criteria passed.
- Give each subagent a self-contained brief: goal, relevant criterion IDs (F/A), the exact sections of this spec it needs (copy them — subagents cannot see Notion either), files it may touch, test commands and expected output format.
- Isolate work: separate Git worktrees or sub-branches off feat/poc-v2-…, or strictly disjoint files. Merge into the feature branch yourself, then rerun affected tests.
- Serialise Framer mutations through one agent at a time. Read-only Framer inspection may run in parallel. Every subagent inherits all safety boundaries in chapter 3: no design canvas, no page breakpoints, no publishing, no default-branch commits.
- Prefer few, well-scoped subagents over many. Do not delegate a task smaller than the cost of briefing it. Stop a subagent that makes no progress after three attempts and bring the problem back to the main loop.
- Record each subagent's task, branch/worktree, result and evidence paths in the criterion ledger.
