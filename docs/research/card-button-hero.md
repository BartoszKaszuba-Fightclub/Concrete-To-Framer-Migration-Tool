# Card, button, and hero

Generic here means the parts that make each of these three things that thing, apart from one site's class names. The first layer is what this repository already emits. The second is the anatomy in the specification that owns the concept. For each one, the last part of the section says which of those parts a builder can read from `tokens.json`, `sections-prompt.md`, `digests/index.json`, the digest files named in the prompt, `consent.json`, and `screenshot.png`. The builder skill forbids the live site, `structure.json`, `computed.json`, and `snapshot.html` (`.cursor/SKILLS/BUILDER.md:36`, `.cursor/SKILLS/BUILDER.md:85`).

## Card

This repository has no component kind named card. The kinds a component record can have are `button`, `field`, and `molecule` (`scripts/generic-extractor/components.ts:9`). The closest kind the code emits for a repeated block is `molecule` (`scripts/generic-extractor/components.ts:158`).

A molecule is a group of visible siblings that share one tag and the same ordered list of child tags. A sibling with no element children is skipped, and so is a sibling whose tag is `header`, `main`, or `footer` (`scripts/generic-extractor/components.ts:27`, `scripts/generic-extractor/components.ts:43`, `scripts/generic-extractor/components.ts:45`). The group is kept when more than one sibling falls in the same bucket (`scripts/generic-extractor/components.ts:51`). The bucket key is the tag plus the ordered child tags (`scripts/generic-extractor/components.ts:46`). The record kind is `molecule`, and the label is the visible text under that node (`scripts/generic-extractor/components.ts:166`, `scripts/generic-extractor/components.ts:169`). The key records those child tags. It does not give them the names media, heading, body, or action.

The fixture that the molecule test calls cards is two `article` elements, each with an `img`, an `h3`, and a `p`, inside a `section` (`tests/extractor/fixtures/requirements.html:41`). The test expects both articles to share one definition whose kind is `molecule` (`tests/extractor/molecules.test.ts:8`, `tests/extractor/molecules.test.ts:30`). The class `card` is on the fixture (`tests/extractor/fixtures/requirements.html:16`). `moleculeGroups` groups by tag and child tags (`scripts/generic-extractor/components.ts:46`).

The HTML element index lists the conforming elements, including `article`, and has no element named `card`. On the fetched index page the only `card` string is the MIME type `text/vcard` ([HTML Living Standard, Elements](https://html.spec.whatwg.org/multipage/indices.html#elements-3), list of elements, and the flow-content category in the same index).

Material Design 3 defines a card as a container of content and actions about a single subject ([Cards guidelines, Anatomy](https://m3.material.io/components/cards/guidelines)). The container is the only required element. A common configuration on that page is container, image, button, supporting text, subhead, and headline. The content-blocks paragraph on the same page says cards can contain a headline, a subhead, supporting text, media, and actions. Media, in the Media subsection, is a thumbnail, an image, or video. Supporting text, in the Text subsection, includes body content such as an article summary. Actions, in the Actions subsection, can be a primary action area, buttons, icon buttons, selection controls, linked text, or an overflow menu.

A digest job copies the record kind onto the job type, so a molecule record becomes a digest whose type is `molecule` (`scripts/digest/jobs.ts:14`, `scripts/digest/generate.ts:228`). `digests/index.json` stores that job type (`scripts/digest/cli.ts:155`, `scripts/digest/cli.ts:163`). The builder may open the index and the digest files the prompt lists (`.cursor/SKILLS/BUILDER.md:36`). Inside such a digest the builder can read each node's tag, its visible text, its box, an image `usablePath`, and each link's label and href (`scripts/digest/generate.ts:187`, `scripts/digest/generate.ts:193`, `scripts/digest/generate.ts:154`, `scripts/digest/generate.ts:704`, `.cursor/SKILLS/BUILDER.md:38`). Those fields are how an image, a headline tag, supporting text, and a button or link show up. The digest has no field named media, headline, subhead, supporting text, or action. `tokens.json` supplies colour and text styles (`.cursor/SKILLS/BUILDER.md:23`, `.cursor/SKILLS/BUILDER.md:24`). It has no card slots. The screenshot is for checking placement, and copy is not taken from it (`.cursor/SKILLS/BUILDER.md:43`). The section prompt may contain the words `card group` and `cards` because the section skill's template uses them (`.cursor/SKILLS/SECTIONS.md:49`, `.cursor/SKILLS/SECTIONS.md:52`). That line is the section agent's prose. The extractor kind on the repeated block remains `molecule` (`scripts/generic-extractor/components.ts:158`).

## Button

`componentKind` returns `button` for a `button` element, for a node whose `role` attribute is `button`, and for an `input` whose type is `button`, `submit`, `reset`, or `image` (`scripts/generic-extractor/components.ts:63`, `scripts/generic-extractor/components.ts:67`). An `a` matches none of those cases and falls through to null (`scripts/generic-extractor/components.ts:71`). Other input types, and `textarea` and `select`, return `field` (`scripts/generic-extractor/components.ts:68`, `scripts/generic-extractor/components.ts:70`). The collected node stores `tag`, `role`, text content, and, for an `input`, a `field` with `type`, `placeholder`, `value`, and `checked` for checkbox or radio (`scripts/generic-extractor/browser.js:71`, `scripts/generic-extractor/browser.js:109`, `scripts/generic-extractor/extract.ts:8`). It does not store `disabled`, `aria-pressed`, `aria-expanded`, or `aria-label` on that node. The component label is the visible text walked from the node (`scripts/generic-extractor/components.ts:78`).

A separate classifier, `controlKind`, runs while a digest is built. It returns `button` for those same input types, and for a `button` element (`scripts/digest/generate.ts:439`, `scripts/digest/generate.ts:441`). For an `a` it returns `button` when the anchor has a visible border or a background that is not transparent, and the subtree has text (`scripts/digest/generate.ts:418`, `scripts/digest/generate.ts:443`, `scripts/digest/generate.ts:444`, `scripts/digest/generate.ts:376`). The same function returns `link` when the subtree has text and the anchor is not painted (`scripts/digest/generate.ts:445`). Its comment says selectors are not used (`scripts/digest/generate.ts:436`). A digest whose type is `button` or `field` keeps its own roots (`scripts/digest/generate.ts:451`). Every other digest scans its nodes with `controlKind`, and the group then stores that kind (`scripts/digest/generate.ts:455`, `scripts/digest/generate.ts:476`). A batch digest whose index type is `button` is planned from the component record's kind (`scripts/digest/jobs.ts:14`). The consent helper's clickable selector includes `a` beside `button` and `[role='button']`, and the value it returns is a dialog or widget frame with a selector and a box (`scripts/generic-extractor/browser.js:272`, `scripts/generic-extractor/browser.js:284`). That frame is not a component kind.

The stored button example has `component.type` `button`, group kind `button`, tag `button`, and a label node whose text is `NL` (`docs/poc-v2/examples/button.digest.json:34`, `docs/poc-v2/examples/button.digest.json:67`, `docs/poc-v2/examples/button.digest.json:88`, `docs/poc-v2/examples/button.digest.json:158`). The section fixture's visible controls are `button` elements labelled Header action, Hero action, and Main action (`tests/extractor/fixtures/sections.html:18`, `tests/extractor/fixtures/sections.html:23`, `tests/extractor/fixtures/sections.html:28`, `tests/extractor/sections.test.ts:34`).

In the HTML Living Standard, the `button` element represents a button labeled by its contents ([The button element](https://html.spec.whatwg.org/multipage/form-elements.html#the-button-element)). The `type` attribute selects submit, reset, or button. The `disabled` attribute makes the control non-interactive and keeps its value out of submission, and activation returns immediately when the element is disabled (same section). The element index describes `button` as a button control and lists `disabled` on it ([Elements](https://html.spec.whatwg.org/multipage/indices.html#elements-3)). That section of the standard does not define a pressed state or an expanded state.

The WAI-ARIA button pattern says a button is a widget that enables users to trigger an action or event, such as submitting a form, opening a dialog, canceling an action, or performing a delete ([Button Pattern, About This Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/button/)). The same page's note says the actions buttons perform differ from the function of a link. Under WAI-ARIA Roles, States, and Properties, the button has role `button` and an accessible label. By default that name is computed from text inside the button. It can also be provided with `aria-labelledby` or `aria-label`. When the action is unavailable, `aria-disabled` is `true`. A toggle button has `aria-pressed`, `true` when on and `false` when off. That property list does not include `aria-expanded`. The disclosure pattern is the one that does: the element that shows and hides the content has role `button`, and `aria-expanded` is `true` when the content is visible and `false` when it is hidden ([Disclosure Pattern, WAI-ARIA Roles, States, and Properties](https://www.w3.org/WAI/ARIA/apg/patterns/disclosure/)).

An `a` element with an `href` represents a hyperlink labeled by its contents ([The a element](https://html.spec.whatwg.org/multipage/text-level-semantics.html#the-a-element)). The element index describes `a` as a hyperlink ([Elements](https://html.spec.whatwg.org/multipage/indices.html#elements-3)). `componentKind` returns null for an anchor (`scripts/generic-extractor/components.ts:71`). `controlKind` returns `button` for a painted anchor that has text (`scripts/digest/generate.ts:444`).

The builder can read, from a digest the prompt lists, `component.type`, the group `kind` and `tag`, the node `tag`, `labelNodes` text, and `text.exact` (`scripts/digest/generate.ts:228`, `scripts/digest/generate.ts:499`, `scripts/digest/generate.ts:197`, `docs/poc-v2/examples/button.digest.json:153`, `.cursor/SKILLS/BUILDER.md:38`). For an `input`, the digest also copies `field`, so `field.type` is there (`scripts/digest/generate.ts:201`). The visible text is the name the builder can read. `aria-label`, `aria-pressed`, `disabled`, and `aria-expanded` are not written onto the node, so those states are not in the allowed files. A section digest can show tag `a` together with group kind `button` for a painted anchor (`scripts/digest/generate.ts:444`, `scripts/digest/generate.ts:499`). `consent.json` is the consent frame, a selector and a box, and the builder places that widget when the file has it (`.cursor/SKILLS/BUILDER.md:42`). The screenshot does not supply the label (`.cursor/SKILLS/BUILDER.md:43`). The current digest writer does not copy `classes` or `domId` onto the node (`scripts/digest/generate.ts:183`). The button example file still has both (`docs/poc-v2/examples/button.digest.json:131`). The builder skill says a class is not on the digest node and points away from `structure.json` for a class or an href (`.cursor/SKILLS/BUILDER.md:45`).

## Hero

`landmarkKind` returns `hero` when the role is `hero` or when the id or class string contains the word hero, and it returns `overlay` when that same node is fixed or sticky (`scripts/generic-extractor/sections.ts:19`, `scripts/generic-extractor/sections.ts:38`, `scripts/generic-extractor/sections.ts:43`). The section candidate stores that string as `kind` (`scripts/generic-extractor/sections.ts:128`). The condition is the role, the id, and the class string (`scripts/generic-extractor/sections.ts:43`). It does not read a heading, supporting text, or an action. The fixture is a `section` with class `hero`, an `h1`, a `p`, and a `button`, and a background colour (`tests/extractor/fixtures/sections.html:8`, `tests/extractor/fixtures/sections.html:20`, `tests/extractor/fixtures/sections.html:21`). The section test expects the candidate kinds `header`, `hero`, `main`, and `footer` (`tests/extractor/sections.test.ts:23`).

Digest jobs give every section candidate the type `section`, using the candidate id and root ids (`scripts/digest/jobs.ts:18`). That job does not read `kind`. The digest copies the job type onto `component.type`, and the index stores the same type (`scripts/digest/generate.ts:228`, `scripts/digest/cli.ts:155`).

The HTML element index has no element named `hero` ([HTML Living Standard, Elements](https://html.spec.whatwg.org/multipage/indices.html#elements-3)). `https://designsystem.digital.gov/components/hero/` returned 404. The definition that did open is the USWDS landing-page template. Under Component definitions it says heroes are used at the top of a landing page to set the tone and help users understand the brand, and that the hero offers a callout with a high-level overview of the site content and will often reference the hero image that sits behind it ([Landing page, Component definitions](https://designsystem.digital.gov/templates/landing-page/)). In that template the hero is a `section` and the first section inside `main`, with an `h1`, a paragraph of short explanatory text, and one call-to-action anchor (same page, the landing-page sample). USWDS settings describe `$theme-hero-image` as the background image for the hero ([Settings, Hero](https://designsystem.digital.gov/documentation/settings/)). The call to action in the sample is an anchor, which the HTML section above treats as a hyperlink.

The builder cannot read `sectionCandidates.kind` without opening `structure.json`, which is forbidden (`.cursor/SKILLS/BUILDER.md:85`). The section skill tells its agent to read `id`, `rootIds`, `memberIds`, and evidence boxes from that file, and its template has a `Role` line whose examples include `hero` (`.cursor/SKILLS/SECTIONS.md:14`, `.cursor/SKILLS/SECTIONS.md:49`). If the written prompt contains `Role: hero`, the builder can read that line because the prompt is an allowed file (`.cursor/SKILLS/BUILDER.md:36`). The builder skill itself uses `Role: overlay` for absolute placement (`.cursor/SKILLS/BUILDER.md:42`).

From the section digest the prompt lists, the builder can read an `h1` through `h6` and its text, a paragraph and its text, a `button` label, a link label and href, `styles.fill.backgroundImage`, and an asset `usablePath` when a background or image URL was saved (`scripts/digest/generate.ts:187`, `scripts/digest/generate.ts:193`, `scripts/digest/generate.ts:560`, `scripts/digest/generate.ts:154`, `scripts/generic-extractor/browser.js:104`, `.cursor/SKILLS/BUILDER.md:38`, `.cursor/SKILLS/BUILDER.md:44`). The digest node stores tag, text, links, and fill (`scripts/digest/generate.ts:187`, `scripts/digest/generate.ts:704`, `scripts/digest/generate.ts:560`). It has no field that marks one action as primary, and no field that marks the band as the first region inside `main`. `tokens.json` does not carry that region. The screenshot is for placement, and copy is not taken from it (`.cursor/SKILLS/BUILDER.md:43`).
